# ADR-0013: パスワードの再設定は、専用の表のトークンとジョブでの送信で行い、申請の画面はアカウントの有無で処理を変えない

- 状態: 採用
- 日付: 2026-10-17
- 関連: 仕様書 第8章「認証」「外部接続」、T25、ADR-0005（Django-Q2）、ADR-0003

## 背景

段階1では、パスワードを忘れた人は管理者が `changepassword` コマンドで仮のパスワードを設定していた（`docs/operations.md`）。
T25 で、本人がログイン画面から再設定できるようにする。要件は、自社 SMTP でリンクを送る、二要素認証は変えない、
アカウントの有無を画面から分からないようにする、申請と完了を監査ログに残す、の 4 つ。

## 決定

- **トークン**: 招待と同じく専用の表（`PasswordReset`）に SHA-256 だけを保存する。一度だけ使え、期限は 60 分。
  新しく発行すると前の未使用のリンクを無効にする。Django 標準の署名つきトークンは使わない（一度だけ・前のリンクの無効化を
  明示的に保証し、監査ログと突き合わせるため）。
- **申請の画面**: アカウントを探さない。入力の形・IP ごとの回数（1 時間 10 回）の確認・監査ログ「申請」・ジョブの登録だけを行い、
  アカウントの有無で処理（流すクエリ）と応答時間を変えない（テストでクエリの数が同じことを固定）。
  上限を超えた申請はジョブを登録しないが、画面の結果は同じにし、監査ログに `rate_limited` で残す。接続元 IP は監査ログと同じ
  `services/client_ip.py`（Cloudflare 経由の扱いも同じ）。
- **送信**: ジョブ（Django-Q2 の `async_task`、`services.jobs.enqueue`）。アカウントの検索・リンクの発行・送信・監査ログ「リンクの送信」
  （元の申請の接続元 IP つき）をジョブの中で行う。有効でパスワードを設定済みのユーザーだけに送る（無効化・招待の受諾前は送らない）。
  同じメールアドレスの有効なユーザーが複数いれば、ユーザーごとに送る（本文にユーザー名）。同じユーザーへは 10 分に 1 通まで。
  単体テストと e2e はジョブを処理するワーカーが無いので、`JOBS_INLINE`（`config/settings_test.py` で真）でその場で実行する。
- **リンクを開く**: トークンをセッションに移し、トークンを含まない URL（`/accounts/password-reset/set/`）へリダイレクトする（Django 標準と同じ方式）。
- **リファラー**: トークンを含む URL の応答（リダイレクト）と、フォームの無い画面（送信済み・完了・無効）は `Referrer-Policy: no-referrer`。
  **フォームのある画面（申請・再設定）は `same-origin`** にする。no-referrer にすると、ブラウザがフォームの送信に `Origin: null` を付け
  （Fetch の仕様）、Django の CSRF の Origin の検査で拒否される（e2e で 403 を確認）。これらの画面の URL にはトークンを含まないので、
  同じサイトへのリファラーでもトークンは漏れない。
- **再設定**: `AUTH_PASSWORD_VALIDATORS` を通す。二要素認証の端末・回復用コードは変えない。ほかの端末のセッションは
  パスワードのハッシュが変わるので次のアクセスで切れる。監査ログ「パスワードの再設定」（パスワードは `***`、無効にしたリンクの ID）。
  完了したら本人に「パスワードが変更されました（日時・心当たりがなければ管理者に連絡）」のメールを送る（ジョブ）。
- **ロック**: 再設定ではロックを解除しない（リンクだけでロックを外せないように）。完了の時点でロック中なら、完了の画面に
  解けるまでの分と「管理者に解除を依頼」を出す（リンクを開けた本人にだけ出るので、アカウントの有無の漏れにはならない）。

## 影響

- 本番では `qcluster` が止まっていると再設定のメールが届かない（ADR-0005 と同じ監視の対象）。
- 監査ログの操作の種類に「パスワードの再設定の申請」「パスワードの再設定のリンクの送信」「パスワードの再設定」を足した。
