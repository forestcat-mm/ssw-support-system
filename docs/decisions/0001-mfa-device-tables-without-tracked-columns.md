# ADR-0001: MFA 端末テーブルに作成者・更新者の列を持たせない

- 状態: 採用
- 日付: 2026-10-16
- 関連: 仕様書 第7章「すべてのテーブルに作成/更新日時・作成/更新者を持つ」、T04b

## 背景

第7章は、すべてのテーブルに作成/更新日時と作成/更新者（本システムでは `TrackedModel` の 4 列）を持つことを求めている。
T04b で導入した多要素認証の端末テーブルは、この形になっていない。

| テーブル | 持っている列 | 持っていない列 |
|---|---|---|
| `otp_totp_totpdevice`（django-otp の TOTP 端末） | `created_at`, `last_used_at` | `updated_at`, `created_by`, `updated_by` |
| `core_recoverycodedevice`（回復用コード一式） | `created_at`, `last_used_at` | `updated_at`, `created_by`, `updated_by` |
| `core_recoverycode`（回復用コード 1 個） | `used_at` | 4 列すべて |

- `otp_totp_totpdevice` は外部パッケージ django-otp のモデルで、列を足すにはフォークか独自モデルへの置き換えが要る。
- `core_recoverycodedevice` は django-otp の `Device` を継承しており、throttling と検証済みセッション（`otp_login`）の仕組みをそのまま使うために同じ構造にしている。
- これらの行を作る・消すのは、常に本人（TOTP の設定、回復用コードの作り直し）か、管理者による MFA リセットだけである。
  作成者は端末の持ち主（`user` 列）と同じになるので、作成者の列は情報を増やさない。

## 決定

MFA 端末テーブル（上の 3 つ）は、第7章の共通列の例外とする。`TrackedModel` を継承せず、作成者・更新者の列を持たない。

「誰がいつ設定・リセットしたか」は、端末テーブルではなく監査ログ（T05 の `AuditLog`）に記録する。
特に MFA リセットは、管理者のアクションと管理コマンド `reset_mfa` のどちらから実行しても必ず記録する。

## 影響

- 端末テーブルだけを見ても、MFA リセットの実行者は分からない。監査ログで追う。
- 新しく作るモデルは、これまでどおり `TrackedModel` を継承する。例外を増やすときは ADR を追加する。
- django-otp を独自実装に置き換える場合は、この ADR を見直す。

## 検討した代替案

- **django-otp をフォークして列を足す**: 上流の更新を取り込みにくくなり、認証という重要な部分で保守の負担が増える。
- **TOTP 端末を独自モデルで実装する**: TOTP の検証・時刻ずれ補正・throttling を自前で持つことになり、誤りの危険が大きい。
- **別テーブルで端末ごとの作成者を持つ**: 監査ログと同じ情報を二重に持つだけで、利点がない。
