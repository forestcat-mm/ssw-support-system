# ADR-0003: TOTP の秘密鍵は列暗号化しない（当面）

- 状態: 採用
- 日付: 2026-10-16
- 関連: 仕様書 第8章（暗号化・バックアップ）、T04b、T06、ADR-0001

## 背景

T06 で在留カード番号・パスポート番号・口座情報の列暗号化（Fernet）を導入した。
一方、多要素認証の TOTP の秘密鍵（`otp_totp_totpdevice.key`）は、django-otp の仕様で DB に平文（16 進文字列）で保存される。

- TOTP の検証には秘密鍵の元の値が要るため、パスワードのようにハッシュにはできない。
- 暗号化するには、django-otp の TOTP 端末を自前のモデルに置き換える必要がある。これは ADR-0001 で「検証・時刻ずれ補正・throttling を自前で持つことになり誤りの危険が大きい」として退けた案と同じである。

## 判断の材料（漏れたときに何が起きるか）

| 漏れ方 | 攻撃者が得るもの | 秘密鍵を暗号化した場合の差 |
|---|---|---|
| 稼働中の DB を読まれる | 秘密鍵に加え、セッションのテーブル（ログイン済みのセッション）も読める | セッションを奪えばパスワードも TOTP も不要なので、差はほぼない |
| アプリのサーバーを乗っ取られる | 暗号化鍵（環境変数）も読める | 暗号化しても復号されるので、差はない |
| バックアップを持ち出される | 秘密鍵とパスワードのハッシュ（PBKDF2）が同時に手に入る | 弱いパスワードを時間をかけて解読されると、両方の要素がそろう。**ここだけ差がある** |

差が出るのはバックアップの持ち出しだけで、これはバックアップ自体を暗号化すれば防げる（在留カード番号以外の個人情報も含むため、どのみち必要）。

## 決定

- TOTP の秘密鍵は、当面は平文のまま（django-otp の標準）とする。
- 代わりに、次の対策を必須にする。
  1. **バックアップを必ず暗号化する。** バックアップの暗号化鍵は、バックアップとは別の場所に保管する（tasks-phase1.md 本番準備）。
  2. **漏洩が疑われたら全員の MFA をリセットする。** `manage.py reset_mfa --all --yes`（T06 で追加。1 人 1 件ずつ監査ログに残る）。全員が次回ログインで TOTP を設定し直し、あわせてパスワードの再設定も求める。
  3. アプリの DB ユーザーの権限を最小にし、DB を外部に公開しない（tasks-phase1.md 本番準備）。

## 見直す条件

- django-otp が秘密鍵の暗号化に対応したとき。
- 本人ポータル（外部公開）を追加し、ユーザー数と攻撃を受ける面が大きく増えるとき。
- バックアップを暗号化できない保存先を使うことになったとき。

## 検討した代替案

- **自前の TOTP 端末モデルで秘密鍵を `EncryptedCharField` にする**: 検証そのものは django-otp の `django_otp.oath.TOTP` を使えるが、端末の検証・時刻ずれ補正・再利用防止・throttling を自前で持つことになる（ADR-0001 と同じ理由で退ける）。上の表のとおり、得られる差はバックアップの持ち出しに限られる。
- **django-otp の列の読み書きを差し替える（モンキーパッチ）**: 上流の更新で壊れやすく、壊れたときに全員がログインできなくなる。
