# 特定技能 登録支援機関 業務管理システム 要件定義書（MVP）

Oct 16, 2026 · @Momoe Yoshinaga

## 1. 背景と目的

登録支援機関の内部業務（台帳管理・期限管理・支援記録・入管提出用帳票の作成）を1つのWebシステムに一元化し、転記・期限漏れ・証跡散逸をなくす。MVPは自社担当者のみが使う内部ツールだが、将来の外国人本人ポータル・受入れ機関ポータルの追加や、同じコードベースでのSaaS化を検討できるよう、業務ロジックと画面を分離した構造にする。マルチテナントなどSaaS固有の設計は今回は行わない。

**解決したい課題**

- 外国人・受入れ機関・契約の情報がExcelや紙に分散し、同じ値を帳票ごとに転記している
- 14日以内の随時届出、3か月ごとの定期面談、在留期限など期限の種類が多く、人の記憶に依存している
- 定期届出（年1回）の裏付けとなる面談記録・相談対応履歴が1年分まとまって取り出せない
- 2027年4月施行の支援体制要件（支援責任者等1人あたり10機関未満・50人未満、常勤・事務所ごと配置）を継続的に確認する手段がない

**MVPで達成する状態**

- 入管のオンライン申請・電子届出に必要な帳票（一括申請用Excel・添付PDF・一括届出用Excel）がシステムから生成され、担当者はアップロードと確認のみ行う
- 期限のあるすべての事項がダッシュボードに出て、超過ゼロで運用できる
- 支援の実施記録が人・日付・項目で検索でき、将来の定期届出集計の元データになっている

**設計上の制約**

- 外部API（入管システム・翻訳・認証SaaS等）には接続しない。入管への提出は人がファイルをアップロードする
- 公式様式は年次で改正される前提で、様式のバージョン管理を持つ
- 個人情報（在留カード番号・パスポート番号等）を扱うため、監査ログと暗号化をMVPから実装する

## 2. スコープ

MVPは「自社担当者だけが使う、自社専用の内部システム」で、まず価値検証を目的に小さく作る。SaaS化は将来の検討事項であり、今回の設計には含めない。

| 区分 | 内容 |
| --- | --- |
| 価値検証MVP（今回作る） | ①外国人・受入れ機関・雇用契約の台帳＋期限ダッシュボード／②支援実績（面談・相談・ガイダンス等）の記録。定期届出で問われる項目を網羅する／③支援計画書・確認書のPDF生成／④一括申請用Excel・一括届出用Excelの生成（様式マスタと版管理を含む）／ユーザー・権限・監査ログ |
| 受入れ機関が5社を超えてから | 定期届出集計／2027年要件（支援体制）モニタリング／初期データ取込（30人規模なら手入力で可）／期限通知メール |
| 将来拡張（設計のみ考慮） | 外国人本人ポータル（スマホ・多言語・自己申告・相談・書類確認）／受入れ機関ポータル（自社の外国人の閲覧・書類提出・面談日程）／同じコードベースでのSaaS化（マルチテナント化はその検討段階で設計する） |
| 非スコープ | 入管システムとのAPI連携／機械翻訳API／ビデオ会議機能の内製（面談URLの保存のみ）／給与計算・勤怠／技能実習・育成就労の監理業務／人材紹介・送り出し機関との連携／マルチテナント・契約プラン・利用量計測などSaaS固有の機能 |

**規模の前提**：自社担当者数名、受入れ機関5社以下（現在2社）、支援対象の外国人50人以下（現在約30人）。この規模で「1つの画面で支援業務が回るか」を検証する。超えた場合も設計は変えないが、後ろ倒しにした機能の着手判断と性能要件の見直しを行う。

| 用語 | 定義 |

| 受入れ機関（特定技能所属機関） | 外国人を雇用する企業。本システムでは「機関」と「事業所」の2階層で管理する |
| 登録支援機関 | 受入れ機関から委託を受けて義務的支援を行う機関。本システムでは自社 |
| 支援責任者／支援担当者 | 支援業務を行う自社の役職員。2027年4月以降は常勤・事務所ごとの配置と人数比率の要件がある |
| 義務的支援（10項目） | 事前ガイダンス／出入国時送迎／住居確保・生活契約支援／生活オリエンテーション／公的手続同行／日本語学習機会／相談・苦情対応／日本人との交流促進／転職支援／定期面談 |

| 定期届出 | 毎年4月1日時点の状況を4月1日〜5月31日に提出する年1回の届出 |
| 様式 | 入管が配布する申請書・届出書・参考様式。本システムでは「様式ID×適用開始日」で版管理する |
| 一括申請用テンプレート | 在留申請オンラインシステムに複数人分を一括登録するための入管配布Excel |
| 一括届出用Excelツール | 電子届出システムに複数対象者分を一括登録するための入管配布Excel |
| 申告値／確定値 | 将来の本人ポータルで本人が入力した値（申告値）と、担当者が確認して台帳に反映した値（確定値）。帳票は確定値のみから生成する |

## 4. 利用者とロール

MVPで実装するのは「テナント管理者」「支援担当者」の2ロール。ただしロールは固定の列挙ではなく、ユーザー×ロールの関係テーブルで持ち、将来ロールは行を足すだけで追加できるようにする。

| ロール | MVP | 主な操作 | 閲覧範囲 |
| --- | --- | --- | --- |
| 管理者 | 実装 | ユーザー管理、様式マスタの更新、全データの閲覧・編集、監査ログ閲覧、2027年要件モニタリング | すべて |
| 支援担当者 | 実装 | 台帳の登録・更新、支援実績の記録、帳票生成、届出タスクの処理 | すべて（担当割当による絞り込みはフィルタのみ） |
| 閲覧者 | 将来 | 参照のみ（経理・監査対応用） | すべて、編集不可 |
| 受入れ機関ユーザー | 将来 | 自社に紐づく外国人の閲覧、書類の確認・提出、面談日程の回答 | 自社機関に紐づくデータのみ |
| 外国人本人 | 将来 | 自己申告、書類の確認・同意、相談、面談回答、お知らせ閲覧 | 本人のデータのみ |

**権限設計の原則（MVPから適用）**

- 権限は「ロール×操作×対象データの範囲」の3軸で判定し、判定ロジックを1か所に集約する。将来のポータル追加時は「本人のみ」「自社機関のみ」の範囲ルールをここに足す
- 個人情報の閲覧は操作として扱い、監査ログに残す（編集だけでなく閲覧も記録）

## 6. 帳票生成要件

帳票生成は本システムの価値の中心で、「確定値のデータ → 様式のセル・欄へのマッピング → 公式テンプレートへの書き込み → 人による確認 → 入管システムへのアップロード」の流れで動く。入管システムには接続しない。

**出力物**

| 出力物 | 形式 | 提出先 | 生成方式 |
| --- | --- | --- | --- |
| 一括申請用テンプレート（記入済） | Excel | 在留申請オンラインシステム | 入管配布の公式Excelを開き、指定セルに値を書き込む。構造・入力規則・保護は変えない |
| 一括届出用Excel（雇用契約届出・支援計画変更届出 等） | Excel | 電子届出システム | 同上（配布ツールのバージョン前提を様式マスタに記録） |
| 支援計画書、事前ガイダンス確認書、生活オリエンテーション確認書、報酬の説明書 等 | PDF | 在留申請オンラインシステムに添付 | Wordテンプレート差し込み、またはHTMLテンプレートからPDF化。パスワード・印刷禁止等の設定を付けない |
| 面談記録書、相談対応記録、支援委託契約書 | PDF／Word | 社内保管・受入れ機関送付 | 同上 |
| 定期届出用の集計表 | Excel／PDF | 電子届出システム・社内確認 | 支援実績からの自動集計 |

**対象分野の上乗せ要件（MVPの2分野）**

MVPで扱う分野は「工業製品製造業分野」と「飲食料品製造業分野」の2つ。いずれも全分野共通の要件に加えて、分野所管省庁の告示による上乗せ基準があり、申請時の添付書類と受入れ機関・登録支援機関の事前要件が変わる。根拠は次の2つの運用要領別冊。

**システムへの反映**

- 受入れ機関の事業所（host\_sites）に、日本標準産業分類コード・分野・登録法人または協議会の加入日と証明書（添付）を持つ
- 自機関（organization）に、食品産業特定技能協議会の加入日と構成員証明書（添付）を持つ（加入済み）。証明書は申請の添付書類として生成リストに自動で含め、有効期限があれば期限ダッシュボードで管理する
- 様式マスタに分野参考様式第3-1号・第13-1号・第13-2号を「分野別添付セット」として登録し、事業所の分野に応じて生成リストに自動追加する
- 書類テーブルに「キャリアアッププラン」（飲食料品製造業分野、契約前に交付）と「実務経験証明書」（両分野、求めに応じ交付）の種別を持ち、交付日・交付方法を記録する
- 業務区分マスタは分野→区分の2階層で持ち、飲食料品製造業分野は2027年4月1日の切替を適用開始日付きで登録する
- バリデーション：加入証明の添付がない場合は「生成不可」、飲食料品製造業分野でキャリアアッププラン未交付の場合は「警告」

**様式のバージョン管理**

- 様式マスタは「様式ID × 適用開始日 × テンプレートファイル × マッピング定義（データ項目 → セル座標または差込タグ）」の組で持つ
- 帳票生成時は申請日・届出日に応じて適用される版を自動選択し、担当者が別版を明示的に選ぶこともできる
- 旧版は削除せず保持し、過去の生成物を同じ版で再生成できる
- マッピング定義はコードではなくデータとして保持し、管理者画面またはJSON/YAMLの取込で更新できる

**生成前バリデーション**

- 様式ごとに必須項目・形式（日付・全角半角・文字数上限）・整合性（在留期限が申請日より後、報酬が契約と一致、支援言語に対応する担当者が存在）のルールを定義する
- 違反があれば生成を止めず「警告付きで生成」と「生成不可」の2段階に分け、不足リストを画面に出す
- ルールもマッピング定義と同様にデータとして持ち、様式の版に紐づける

**生成履歴**

- 生成ごとに、対象の外国人・様式ID・様式版・使用したデータのスナップショット・生成者・生成日時・出力ファイルを保存する
- 同じ内容の再生成は履歴に別エントリとして残す（上書きしない）
- 履歴から「このファイルがどのデータから作られたか」をたどれること

## 7. データモデル

すべてのテーブルに作成/更新日時・作成/更新者を持つ。個人情報の値は暗号化列に格納する。履歴が必要な項目（在留情報・住所・雇用契約・支援計画）は上書きせず版または履歴行として保持する。

外国人（foreign\_workers）を起点に、在留履歴・支援計画・支援実績・雇用契約・届出・生成帳票がすべて worker\_id でぶら下がる。受入れ機関側は「機関→事業所→雇用契約」、自機関側は「機関→事務所→支援責任者等→ユーザー」と階層をたどる。各テーブルの項目は次の表のとおり。

| テーブル | 主な項目 | 設計上の注意 |
| --- | --- | --- |
| organization | 自機関の名称、登録支援機関登録番号、登録期限、所在地 | 1行。登録更新期限の管理元 |
| users / user\_roles | ユーザー、ロール、MFA設定、招待状態 | ロールは行で追加できる構造。本人・受入れ機関ユーザーは将来ここに乗る |

| foreign\_workers | 氏名（ローマ字・漢字・母国語）、国籍、生年月日、性別、支援言語、担当者、状態（入国前／在留中／離職／帰国） | 将来の本人ログインに備え users との紐づけ列を持つ |
| residence\_records | 在留カード番号、在留資格、在留期限、許可日、申請種別 | 履歴行。最新行を参照ビューで取る |

## 8. 非機能要件

内部利用のMVPでも、扱うのが在留カード番号・パスポート番号・住所を含む個人情報であり、将来は外部公開のポータルになるため、セキュリティと監査はMVPの時点で本番水準にする。

| 分類 | 要件 |
| --- | --- |
| 認証 | 前段にCloudflare Access（メールのワンタイムコード等）を置いて管理画面全体を保護し、アプリ側でも管理者・担当者は多要素認証を必須。パスワードはハッシュ化保存。一定回数の失敗でロック。セッションは無操作で失効 |
| 認可 | ロール×操作×データ範囲で判定。判定ロジックは1か所に集約。将来のポータル追加時はデータ範囲のルールを追加する |
| 暗号化 | 通信はTLS1.2以上。在留カード番号・パスポート番号・口座情報は列暗号化。鍵はアプリ外で管理 |
| 保存しないデータ | マイナンバーは保存しない（必要な場面は紙運用に切り離す） |
| 監査 | 閲覧・作成・更新・削除・帳票生成・エクスポートをすべて記録。ログは改変不可の保存先に書き出し、最低5年保持 |
| データ保持 | 退職・帰国後の保持期間と削除手順を定義し、期限到来をダッシュボードに出す。入管の記録保存義務期間を下回らない |
| バックアップ | 日次バックアップ、別リージョンまたは別アカウントに保管、四半期ごとに復元テスト |
| 可用性 | 平日日中の業務時間帯で稼働率99.5%以上を目標。計画停止は事前告知 |
| 性能 | 一覧表示は2秒以内、帳票生成は1件あたり10秒以内（50人規模ではこれで十分。一括生成の性能要件は規模拡大時に設定） |
| 対応環境 | PC：Microsoft Edge・Google Chromeの最新版。入管配布Excelの動作前提（Microsoft 365／Excel 2016）は様式マスタに記録 |
| ホスティング | 国内リージョン。個人情報保護法および入管への委託先としての管理義務を満たす設定 |
| ログ・監視 | アプリケーションログ、エラー通知、ストレージ容量監視 |
| 運用 | 様式改正時の様式マスタ更新手順、ユーザー追加・退職時の手順、障害時の連絡手順を文書化 |
| 外部接続 | 外部APIは使わない。例外は自社管理のSMTPサーバーによるメール送信のみ |

## 9. 拡張性の設計方針

今回は自社専用システムとして作る。将来のポータル追加やSaaS化で変わるのは「画面」と「誰がどこまで見えるか」だけで、業務ロジックとデータ構造は変えずに済む構造にしておく。SaaS固有の仕組み（マルチテナント、契約プラン、利用量計測）は今回は作らず、その検討段階で設計する。

&#91;embedded content: システム構成 · MVPと将来の層\]

上段の画面を足すとき、認証・認可層にロールとデータ範囲のルールを足すだけで、下段のサービス層とデータ層はそのまま使う。

**今回守ること（コストのかからない範囲）**

- 業務ロジック（期限計算、帳票マッピング、バリデーション）を画面やフレームワーク依存のコードから分離し、サービス層として独立させる
- 自社固有の設定（支援言語の選択肢、メール送信元、自社名・登録番号、ロゴ）はコードに埋め込まず設定テーブルまたは設定ファイルに持つ
- 様式マスタとバリデーションルールはデータとして持ち、コード変更なしに差し替えられるようにする

**場所に依存しないコードの5原則**（本番サーバーをVPS・Lightsail・EC2のどれにしても、コードを変えずに済ませるため）

1. 環境ごとに変わる値（DB接続先、ストレージ、SMTP、暗号化鍵、許可ドメイン）はすべて環境変数で渡し、コードに書かない。手元は `.env`、本番はサーバーの環境変数
2. ファイル保存は `django-storages` で抽象化し、手元はローカルディスク、本番はS3互換ストレージ（S3・R2・さくら）を設定だけで切り替える
3. Word→PDF変換は `convert(docx) → pdf` の1関数に閉じ、裏で同居のLibreOfficeを呼ぶか別コンテナのHTTPを叩くかを設定で決める
4. 同じ `docker-compose.yml` を手元と本番で使い、差分は `.env` と本番用オーバーライドファイルに閉じ込める
5. DBの構造変更はDjangoのマイグレーションで管理し、どのサーバーでも `migrate` で同じ状態にする

**ポータル追加に備える**

- 外国人・受入れ機関のレコードにユーザー紐づけ列を持ち、「本人のみ」「自社機関のみ」のデータ範囲を権限ルールとして表現できるようにする
- 本人入力は「申告値→担当者確認→確定値」の二段構えを前提にし、確定値のテーブルに「最終確認者・確認日時」をMVPから持つ
- UI文言は言語リソースファイルで管理し、MVPの管理画面も日本語リソース経由で表示する（ハードコードしない）
- フロントエンドはレスポンシブで作り、本人ポータルは同じコードベースの別ルートとして追加できる

**SaaS化に備える**

- SaaS化を本格検討する時点で、マルチテナント化（契約単位の分離、契約プラン、利用量計測、運営者ロール）を別途設計する。現時点のデータ構造にテナント列などを先行して入れない
- そのときの移行を軽くするために、今回は「自社固有の値をコードに埋め込まない」「業務ロジックを分離する」の2点だけを守る
- データのエクスポート（全テーブルのCSV出力）はバックアップ目的で今回も用意し、将来の移行手段を兼ねる

## 10. 技術スタック案

帳票生成（Excel・Word・PDF）のライブラリが充実していることを最優先に、バックエンドはPythonを推奨する。確定ではなく、開発体制に合わせて置き換えてよい。

| 層 | 推奨 | 理由・代替 |
| --- | --- | --- |
| バックエンド | Python（Django） | 管理画面の素地（Django admin）、認証・権限・監査の実装が早い。代替：FastAPI＋SQLAlchemy |
| Excel生成 | openpyxl | 入管配布テンプレートを開いてセルに書き込める。マクロ付きの場合は `keep_vba=True` で保持を確認 |
| Word→PDF | docxtpl ＋ LibreOffice（headless、同じサーバーにDockerで同居） | 参考様式がWord配布のため。変換は1関数に閉じ、将来は別コンテナやCloudflare Containersに切り出せる |
| データベース | PostgreSQL（当面は同じサーバーのDocker。日次ダンプをオブジェクトストレージへ） | JSON列（マッピング定義）、暗号化拡張。規模拡大時はマネージドDB（RDS等）へ接続先変更だけで移行 |
| フロントエンド | React（Next.js または Vite） | 管理画面は Django テンプレートでも可。将来の本人ポータルを同じコードベースのルートで追加するためReactを推奨 |
| 認証 | Cloudflare Access（前段）＋Django標準＋TOTP（多要素） | 外部IDaaSは使わない。Accessの無料枠（50ユーザーまで）で管理画面全体を保護 |
| ファイル保存 | `django-storages` 経由。手元はローカルディスク、本番はS3互換ストレージ | 置き場は未決（S3東京／さくらのオブジェクトストレージ／R2）。設定値の変更だけで切替 |
| ジョブ実行 | Celery または Django-Q ＋ Redis | 帳票生成、日次バックアップ |
| メール | 自社管理SMTP（開発中はMailpit等のメールキャッチャー） | 期限通知メール自体は後ろ倒し |
| インフラ | サーバー1台（国内VPS または AWS Lightsail、メモリ4GB）に Docker Compose。Cloudflare Tunnel で公開し、サーバーのポートは開けない | 月額目安：国内VPS 1,500〜3,000円／Lightsail 約4,000円。Cloudflareは無料枠。規模拡大時にRDS・ECSへ段階移行 |
| 設定管理 | 環境変数（`.env`）と本番用 docker-compose オーバーライド | 第9章「場所に依存しないコードの5原則」 |
| 監視・ログ | 標準のアプリログ＋ログ集約（OSS） | 監査ログはDBとは別に追記専用ストレージへも書き出す |

## 12. 前提・リスク・未決事項

**前提**

- 入管のオンライン申請・電子届出の利用申出は済んでいる、または並行して行う（システム利用には別途承認が必要）
- 入管配布の一括申請用テンプレート・一括届出用Excelツールの最新版を入手し、セル構造を解析できる
- 支援言語ごとの確認書テンプレートは自社で用意する（翻訳は人が行う）
- 2027年4月の支援体制要件（常勤・事務所ごと・1人あたり10機関未満/50人未満・養成講習）は現時点の公表内容に基づく。省令の最終内容で見直す
- 支援言語は中国語（簡体字）。確認書・ガイダンス資料のテンプレートは日本語と中国語の2言語で用意し、他言語は受入れ状況に応じて追加する
- 対象分野は工業製品製造業分野と飲食料品製造業分野。自社は食品産業特定技能協議会に加入済みで、両分野とも長期間の支援実績がある

**リスク**

| リスク | 影響 | 対策 |
| --- | --- | --- |
| 入管の様式・テンプレートが改正され、生成物が取り込めなくなる | 申請遅延 | 様式マスタの版管理、改正ウォッチの月次定例、改正時の検証手順 |
| 配布Excelの保護・マクロ・入力規則を書き込みで壊す | 取込エラー | テンプレートを開いて値だけ書く方式に限定し、生成後に人が開いて確認する運用 |
| 個人情報の漏えい | 法令違反・信用失墜 | 列暗号化、多要素認証、閲覧の監査ログ、保持期間と削除手順 |
| 既存Excel台帳からの移行時にデータ不整合が出る | 誤った帳票 | 取込時のエラーレポートと担当者確認、移行後1か月の並行チェック |
| 将来のSaaS化を見越した設計が過剰になりMVPが遅れる | 立ち上がり遅延 | SaaS固有の設計は行わず、業務ロジックの分離と設定の外出しに留める（第9章） |
| Claude Codeで内製するため、動作確認が形式的になり不具合が残る | 全体遅延 | 各段階のゲートで人がダミーデータを使って実際に操作し、生成物は様式と目視で見比べる。1タスク1コミットで戻れる状態を保つ |

**未決事項**

- [ ] 本番サーバー1台の借り先：国内VPS（さくら・ConoHa等、月1,500〜3,000円）か AWS Lightsail（4GB、月約4,000円）。構成・コードはどちらでも同じで、Cloudflare Access＋Tunnelを前段に置く
- [ ] 添付ファイル・バックアップの置き場：国内に揃える（さくらのオブジェクトストレージ・S3東京）か Cloudflare R2（アジア太平洋まで指定可、国内固定は不可）か、当面VPS内ディスクか
- [ ] 対象分野：工業製品製造業分野・飲食料品製造業分野で確定（第6章「対象分野の上乗せ要件」参照）。自社は食品産業特定技能協議会に加入済み
- [ ] 退職・帰国後のデータ保持期間（社内規程として決める）
- [ ] 定期面談のオンライン実施の方針（ツールと同意の取り方）
